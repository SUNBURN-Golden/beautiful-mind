# Ethereum L1-Readiness Hardening v1 Architecture

This document defines the core architecture, privacy constraints, and cryptographic guarantees mapping the central SoulBound database (`audit_logs`) to mathematically verifiable Ethereum L1 Merkle Anchors.

## 1. Single Source of Truth (SSOT)
- **Source of Truth:** `public.audit_logs` (Append-only).
- **Target Commitment:** `public.merkle_anchors` connected to Ethereum L1 via `anchor_submissions`.

## 2. Privacy Filtering Guidelines (Zero-Knowledge Hash Concept)
The core objective is projecting pipeline events to L1 without exposing Personally Identifiable Information (PII) or emotional context. Instead of a risky blacklist approach, we strictly enforce a **Metadata + Payload Hash Allowlist**:
1. `canonical_json` contains ONLY structural metadata (`audit_id`, `table`, `record`, `action`, `user`, `timestamp`) and cryptographic hashes (`new_hash`, `old_hash`).
2. **Payload Hash Rules:** `new_hash` and `old_hash` are generated by passing the *entire* raw `new_data` and `old_data` (including PII) into the `deepStableStringify` utility, and hashing the resulting string using `ethers.keccak256`. 
3. **Tamper Detection Mechanism:** Mutating any PII within the raw `audit_logs` will immediately mutate the `new_hash/old_hash`, thus altering the `receipt_hash_keccak` and breaking the Merkle Root validation without ever exposing the raw text to the L1 pre-image.

## 3. Canonical Serialization Rules (Determinism)
To guarantee strict deterministic determinism across JS, Python, or Go verifiers constructing the Merkle Tree:
1. Construct the `canonical_json` using exactly the following shape:
   `{ action, audit_id, event_type, meta, new_hash, old_hash, record, schema_version, table, timestamp, user }`
2. **Deep Stable Stringification:** Standard `JSON.stringify` does not guarantee nested key order. The `deepStableStringify` utility recursively sorts all object keys alphabetically and perfectly maintains array sequences, outputting a completely deterministic mathematical string for both the `canonical_text` and payload hashing.

### 3.1 Schema Versioning (Future-Proof Soft-Lock)
- The current implementation is strictly locked to `schema_version: 1`. 
- **Rule of Expansion:** v1 is a "soft-lock". If future Ethereum smart contracts require additional fields (e.g., L2 bridging signatures, ZK proofs), they MUST NOT alter the v1 schema structure. Instead, the ETL pipeline must start emitting `schema_version: 2` with the new fields, ensuring historical Merkle Roots from v1 remain mathematically valid and backward-compatible.

## 3.2 Concurrency and Incremental Watermarking
- **Concurrency (Duplicate Anchor Prevention):** The `event_receipts` table inherently guards against race conditions via a `UNIQUE(source_table, source_id)` constraint. The `merkle_anchors` table enforces `UNIQUE(source, batch_end, schema_version)`.
- **Incremental Processing:** The ETL `merkle-snapshot` API dynamically fetches the `last_audit_id` from the most recent `merkle_anchors` execution and sequentially loads only new `audit_logs` where `id > last_audit_id` to strictly bound memory overhead and DB load.

## 4. Sorting and Merkle Inclusion
- **Leaf Hashing Algorithm:** `ethers.keccak256(ethers.toUtf8Bytes(canonical_text))`
- **Leaf Sorting Rule:** `event_receipts` are ingested into the leaf arrays ordered strictly by `occurred_at ASC, source_id ASC`. 
- **Binary Root Construction:** The array of hashes constructs pairwise hashes `ethers.keccak256('0x' + left + right)`. If the array contains an odd number of items, the final item gets cleanly promoted up a layer without hashing.

## 5. Event Type Specification (Immutable)
To normalize actions for EVM L1 ingestion, standard `token_ledger` events are locked into fixed string terminologies:
- **매칭 신청 비용 (Matching Registration)**: `'GAS_FEE_BURN'`
- **프로필/결과 확인 비용 (Review Unlock)**: `'UNLOCK_FEE_BURN'`
- **일반 슬래싱 비용 (System Slashing)**: `'SLASHING_BURN'`
- **일반 파이프라인 진행**: `[TABLE]_[ACTION]` (e.g., `REVIEW_SIGNATURES_INSERT`)

*Note: The core DB `token_ledger.type` enum REMAINS unaltered (`SLASHING_BURN`, `GAS_FEE_BURN`) to prevent breaking changes on DB schema. Transformation into `UNLOCK_FEE_BURN` happens exclusively inside the Node.js `merkle-snapshot` ETL routing by checking the idempotency key prefix.*
